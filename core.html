core

The vault: one SQLite file that holds everything you have collected, and the search over it

A vault is one SQLite file that holds everything you have collected, such as web pages, papers, talk transcripts, PDFs, notes and source files, all searchable together. Vault() opens ~/.vishalakshi/vault.db, Vault(path) opens or creates any other file, and Vault(':memory:') makes one that lasts only as long as the process.

A Vault is a litesearch Index, and litesearch decides how text is stored and found. Each thing you add becomes a document. A document is split along its headings into a tree of sections, which litesearch calls nodes, and each section’s text is cut into chunks. Every chunk is stored twice: as text, for SQLite’s full-text keyword search, and as a vector, a list of numbers from an embedding model that puts texts with similar meanings near each other. A search runs both and merges the two rankings with reciprocal rank fusion (RRF), which scores each chunk by its rank in each list rather than by the raw scores, because a keyword score and a vector distance cannot be compared. The default embedding model is potion-multilingual-128M, which is small, fast and covers over 100 languages, Devanagari among them; encoder= picks another (see concepts).

The vault adds to that a kind on every document, saying how it arrived (web, pdf, arxiv, note, code and so on), shelves that keep separate collections in the same file, marks that record a person’s judgements about a document, an entity graph and topic map, and the methods on the other pages that fetch, read, extract and answer.

Add text, pages, a file or a directory to the vault, adding a source again only when its content changed.

search returns chunks: each hit is a short snippet with the node_id of its section and the doc_id of its document. sections ranks whole sections instead. context is what to hand a language model: whole sections with their text, each with a breadcrumb (the path of headings down to it, such as Attention › Multi-head) and a node_id that read turns back into the full section. Its related list holds sections found by vector similarity to the results rather than by matching the question, as leads. context also adds a couple of sections from each other shelf (shelves=2), and code sections (code=) when kosha has indexed the repository. rerank=True reorders the hits with a cross-encoder model, which needs the rerank extra (pip install 'vishalakshi[rerank]').

These methods, and read and document, take pii=, which is off unless you set it; see pii. Every row also carries age, the seconds since its document was filed, and stale, and stale rows sort last.

A node_id names a section and a doc_id names a document. doc(ref) finds a document’s row by its id, its exact source, or part of its title. document(ref) rebuilds a whole document in reading order with its headings put back, which is what a model reads to extract fields from; given a path the vault has never seen, it reads the file from disk. read(node_id) rebuilds one section, and toc and sections walk the tree.

A document’s meta holds where it came from and anything set with set_meta, such as its doctype. Adding a changed document again rewrites its meta, so a lasting judgement about a document goes in the doc_marks table instead (see Marks below).

Shelves

One vault file can hold several shelves. A shelf is a separate collection with its own chunks, section tree and vector index, so a large corpus on one shelf, say a thousand papers, does not crowd a small one out of the rankings. shelf(name) opens a shelf, creating it the first time. A shelf keeps the embedding model it was first written with, and reopening it with a different one raises an error, since vectors from two models cannot be compared. shelves() lists the shelves with their models and document counts, and drop_shelf deletes one. The main shelf is called store. SHELVES names the ones the vault itself uses: store, papers, sanskrit, code and data. Acquisition sends some kinds to their own shelf through KIND_SHELF, below.

Marks

A mark is a judgement about one document, kept in the doc_marks table so it survives the document being added again. There are three. noisy is for junk such as a cookie banner or a site footer, which search, sections, context and ask then leave out. pii_override holds the privacy marks described on pii. stale says a document no longer matches its source; search still returns it, flagged and sorted last, and the mark is lifted when the document is added again with new content. mark sets any of them, and mark_noisy, mark_stale and the pii methods are the named ways to do it. marks() lists every mark on the shelf and marks(ref) gives the one on a document.

A shelf opened from a vault shares the vault’s embedding model in memory, so opening many shelves loads the model once. offline=True, or $VISHALAKSHI_OFFLINE, carries over to a new shelf as well, so an offline vault never downloads a model.
