pii

Find personal information in the vault, give each document a privacy level, and control what retrieval hands back

Personal information, often called PII, is text that identifies a person or opens one of their accounts: an email address, a phone number, a card or bank account number, a national identity number such as a UK National Insurance number or an Indian Aadhaar number, a street address, a date of birth, an API key or password. The detector is a separate package, rahasya. It works with patterns and checksums rather than a model. A card number has to pass the Luhn check and an NHS number its mod-11 check, so the detector gives the same answer every time and downloads nothing. On a held-out test set of 240 generated documents it missed nothing and raised no false alarm (evals/RESULTS.md, section 3).

Names are the gap. No pattern describes a name, so name detection is a second pass, and it finds only a name that follows a title such as Mr, Dr or Prof: “Dr Charles Babbage” is found, “Ada Lovelace” on her own is not. The pass runs when a document is added (except on code, where identifiers are not names) and by default in ask; Vault.pii and gated run it only with ner=True. When a document holds personal information the detector cannot see, a person marks it, as below.

This page is the half of the work that needs a vault: the marks a person sets, the privacy level of each document, the table of findings, and gated, which applies a policy to what search and reading return. What ask and the other model calls send to a model is on ask.

Checking a document, and gating retrieval

Vault.pii(ref) answers for one whole document: whether it holds personal information, which kinds, and whether a person’s mark overrides the detector. detected is the detector’s own verdict and override is the mark. mark_pii marks a document as personal when the detector finds nothing, for example a letter that names people without titles. mark_not_pii clears a false alarm, such as your own invoice, and only a person may set it (see the next section). pii_ctx runs the detector over every section of an assembled context, the result of context, which is what ask decides on.

Retrieval is the other half. search, sections, context, read, document, toc, doc_context and federate all take pii=, which says what happens to a row that holds personal information:

pii= the row’s text becomes
off, the default in Python and the CLI the stored text; nothing is checked
redact the stored text with each recognised identifier replaced by its kind, as in [EMAIL]
refuse a placeholder such as [withheld: personal information (card, email)]

Under redact and refuse the row stays in the results, its title and breadcrumb are masked rather than removed, and a pii key names the kinds found, so a caller can still say why something was held back. Three cases follow from the levels below. A Local only document is withheld under redact as well as refuse, and so are its title, breadcrumb and source. A document that is private only because of a mark or the shelf’s floor, with nothing the detector recognises, passes through redact unchanged, because there is nothing to mask; use refuse when that matters. A document a person cleared with mark_not_pii comes back untouched, unless the shelf’s floor is above Open.

The MCP server hands its results to a model the vault does not run, so there every tool defaults to redact, and every result is gated whatever the tool, including ask’s. A client may ask for refuse. It may not ask for off.

Learned detectors were measured and not shipped

Two learned PII models, an ONNX build and a TFLite build, were tried against the patterns. Both were worse on precision and on recall, and about 200 times slower, so the shipped detector is the patterns alone. The model code stays in evals/backends.py, evals/pii_model.py reruns the comparison, and evals/RESULTS.md has the numbers.

Privacy levels and findings

Every document has one of three privacy levels. The level decides what this package’s own model calls may send to a model that runs somewhere other than this machine, called a hosted model below.

level how a document gets it what a hosted model may be sent
Open (open) nothing personal found, or a person cleared it the text as it is
Personal (personal) the detector found an identifier, or someone marked it it depends on the policy: masked text, nothing, or with allow=True the whole text (see ask)
Local only (local) someone set it with set_level, or its type is sensitive nothing; only a model on this machine reads it

The sensitive types come from varga: passport, ID card, bank statement, payslip, tax return and clinical record. These rules cover what vishalakshi sends to models. In Python and the CLI they do not stop retrieval: read or search with the default pii='off' still returns a Local only document’s text to whoever called it. The MCP server defaults to redact, which withholds it.

level(ref) works a document’s level out in three steps. A mark set with mark_pii, mark_not_pii or set_level, if there is one, decides. Otherwise the level is the higher of the type’s level and the findings’ level, where any identifier found in its text or its title makes it Personal. Finally the result is raised to the shelf’s floor. The floor is a level no document on the shelf can go below, set with set_floor. A shelf for medical records can have a floor of Local only, so a new document there is protected before anything has been detected in it. level(ref, page=n) gives one page’s level from that page’s findings; a page with no text takes the whole document’s level.

Raising a level is always allowed. Lowering one is not. set_level to a lower level, removing a mark, mark_not_pii, reject_pii, reset_pii and lowering a floor all take by= and raise PermissionError unless by='person'. The default is 'person', so a person’s own code passes nothing, and an agent passes its own name. The MCP server does not offer by, so a model client cannot claim to be a person, and it cannot turn the retrieval gate off with pii='off' either.

When a document is added, scan_pii scans each page and files every identifier in the pii_findings table as a finding: its kind, its page, its start and end offsets in the page text, and a fingerprint. The fingerprint is a 16-character hash of the kind and the value with spacing, dashes and case removed, so ADA@example.com and ada@example.com, or 4111-1111-1111-1111 and 4111 1111 1111 1111, give the same fingerprint. The table does not hold the value. The value is still in the document’s text, which the vault keeps as it was read, and the hash has no secret key, so a short value such as a date of birth could be recovered by hashing every possible one. Treat the findings table as exactly as private as the vault file. findings lists them, each with a masked preview such as a••@e••••••.com taken from the current page text.

A person can give a verdict on a finding. accept_pii confirms it is personal, which an agent may also do, since it can only raise a level. reject_pii says it is not, and the level falls if nothing else holds it up. reset_pii takes a verdict back. A verdict is stored against the fingerprint, so it covers every occurrence of the same value in the document and it survives the page being read again: the new findings get new ids and keep the old verdict. A finding id from before the re-read comes back as stale.
