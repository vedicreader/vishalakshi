ask

Answer questions from the vault with a local or hosted model, cite the sections used, and check what each model is sent

To answer a question the vault needs a language model. Urai is the chat interface vishalakshi talks to, and Rishi supplies the backends behind it, registered the first time a chat is built. A model is named by an id, and the id picks the backend: LiteRT, MLX, llama.cpp or Ollama on this machine, or a hosted API such as claude/sonnet or gpt-4.1-nano. With no id the vault uses gemma-4-E2B, a small model that runs on this machine through LiteRT and needs no API key. LiteRT is asked for the GPU and falls back to its default backend, with a warning, when there is none. $VISHALAKSHI_MODEL names a different default and $VISHALAKSHI_GPU=0 keeps LiteRT on the CPU. Anything else the chat constructor takes, such as a temperature, goes in chat_kw=.

Build the prompt the model reads: the numbered sections, the related leads by title, then the question.

Answering with citations

ask(question) retrieves the sections of the vault that best match the question with context. mk_prompt numbers them [1], [2] and so on, and lists the related sections (neighbours found by vector similarity rather than by the question) by title only, as leads. The system prompt VAULT_SP tells the model to answer only from the sections and to cite the number of each one it used. ask returns the answer with cited, the sections the answer actually cites, each with the node_id that read opens. sections=4 and max_chars=1500, the characters kept from each section, are the context budget.

To ask about particular documents, pass ref= with one or more of them, or use ask_doc from extract. doc_context then puts the named documents first, whole, as sections [1] to [n], sharing doc_chars characters between them, and adds a few sections from the rest of the vault behind them.

The line that tells the model which numbered sections are the documents being asked about.

mk_chat= lends ask a chat a host already has running, such as a model an app has loaded, instead of building a new one. The privacy check looks at the chat that was actually built, so a hosted chat lent by mistake is still treated as hosted.

Sections count as private when the detector finds identifiers in them, when a document is marked, or when a document’s level is above Open for any other reason, such as its type or the shelf’s floor. Before anything is sent, related leads that hold personal information are dropped, and so are retrieved sections that do when ref= named the documents. pii= then decides what happens to the rest:

pii= what happens when the sections are private
local a model on this machine answers: pii_model, else $VISHALAKSHI_PII_MODEL, else the default model, under PII_SP, a system prompt that forbids repeating any personal detail. If that chat is not local, nothing is sent and the answer says so
redact the recognised identifiers in each section’s text, heading line, title and source are masked, then the named model answers, hosted or not
refuse no model is asked, and the answer says what was held back

The default is local when a local runtime is installed and redact when none is. ask has no off: pii='off' warns and applies the default. The result’s policy says which one ran. Under every policy a hosted model gets a Local only section as a bare [n] [withheld: local only] line, with no heading, title or source (see send_check below). Under redact, names with no title such as Dr before them are not masked. Name detection is on by default (pii_ner=True). Whatever a model answers over private sections is scanned again on the way out, any identifier it repeated is masked, and leaked lists the kinds. The result also carries the prompt and the context the model read. Under local they hold the private sections whole, so a host that hands the result to a hosted model passes on answer and cited only.

Deciding what a model may be sent

send_check decides, before anything goes to a model, how each document, page or piece of text goes: whole, masked, or not at all (withheld). It returns the decisions in rows, the subsets send, masked and withheld, and a why sentence for a person to read before sending, for example gpt-4.1-nano, hosted. 1 personal document masked, 1 document open, 1 local-only document withheld. The rule itself is send_rule:

  • A model on this machine gets everything whole. model_local decides what counts as local: LiteRT, MLX and llama.cpp always, Ollama only when $OLLAMA_HOST points at this machine. Anything else, including a chat that names no runtime, is hosted.
  • An Open item goes whole to any model.
  • A Local only item is withheld from a hosted model under every policy, even with allow=True.
  • A Personal item goes to a hosted model masked under redact, and is withheld under local and refuse. A page image cannot be masked, so a Personal page image is withheld under every policy except off.
  • allow=True, allow once, sends Personal items whole for that one call, as policy='off' does.

ask, explain, categorize, extract, read_doc, reparse and proofread all decide through this rule. The decision covers everything that goes with the text: a document’s title, its headings and its source path are masked with it or withheld with it. A page image is read with the document’s title in its prompt, so the title is judged with the page. build_graph, and connect through it, sends every chunk to its chat with nothing to mask, so a hosted chat builds the graph only when every document on the shelf is Open; otherwise nothing is sent and the result says why. Masking replaces only what the detector recognises. A document marked Personal by hand, with nothing recognisable in it, therefore goes to a hosted model under redact exactly as it is stored.

Each send to a hosted model is recorded in the vault’s send_log table: when, which document and pages, which model and runtime, the policy, and the kinds of personal information where they are known. sends(ref) reads it back, newest first. Sends to a local model are not logged, and withheld items are not in the log.

Recording what a model said

CachedChat records a model’s replies on disk and plays them back, so tests and these pages can show real answers without running the model again. Give it a folder of recordings and the vault treats it as any other chat. The folder is path, else $VISHALAKSHI_CHAT_CACHE, else chatcache in the working directory. A question with no recording raises an error unless $VISHALAKSHI_RECORD_CHAT is set. Then the question goes to the real model and the reply is recorded, so the next run answers from disk. Building one registers Rishi’s runtimes, as new_chat does, so runtime names the backend of the id without building an engine.

The default budget is sections=4 and max_chars=1500. Six sections of 4,000 characters each overflowed the context window of the 2B default model, and LiteRT reported that as a send failure with no explanation (evals/RESULTS.md). When a send fails that way, ask warns and tries once more on a new chat, with the first two sections at a third of the length and no leads.

When the sections hold personal information

The detector and the marks are explained on pii. The cells below show what ask does with them. They use a stand-in chat that records what it was sent, so a leak would show up as a recorded call.

The check runs on the chat that was built, before anything is sent. Here a hosted chat is lent under the default local policy, so the model is never called.

_seen.clear()
r = _v.ask('what is on invoice 4471?', mk_chat=_chat('remote', 'THIS MUST NEVER BE SENT'))
test_eq(_seen, {})                       # the model was never called at all
test_eq(r.refused, True)
r.answer
'held back: these sections hold personal information (card, email, phone) and remote is not a local runtime, so nothing was sent to it'

With a local runtime the private sections go to the local model under PII_SP, which tells it to answer with counts, kinds and totals instead of personal details, and to say what it held back.

_seen.clear()
r = _v.ask('what is on invoice 4471?', mk_chat=_chat('litert',
    'One invoice, 240.00 GBP, due in September. Holding back the name, email, phone and card. '
    'Tell me what you need: a total, a due date, or a yes/no.'))
test_eq(_seen['runtime'], 'litert')
test_eq(_seen['sp'], PII_SP)             # not VAULT_SP: that one tells it to cite, and a citation points at the text
test_eq(r.get('refused', False), False)
r.answer
'One invoice, 240.00 GBP, due in September. Holding back the name, email, phone and card. Tell me what you need: a total, a due date, or a yes/no.'

instruction= sends a follow-up turn. When the local model holds something back it says which instruction would let it answer, such as “give me the total and the due date”, and the caller sends that instruction with the same question.

_seen.clear()
r = _v.ask('what is on invoice 4471?', instruction='Give me the total and the due date only.',
           mk_chat=_chat('litert', 'Total 240.00 GBP, due 2026-09-01.'))
test_eq('Instruction from the questioner' in _seen['prompt'], True)
r.answer
'Total 240.00 GBP, due 2026-09-01.'

Every answer over private sections is scanned again before it is returned. Identifiers the model repeated anyway are masked, and leaked lists their kinds.

_seen.clear()
r = _v.ask('what is on invoice 4471?',
           mk_chat=_chat('litert', 'It is for ada@example.com, card 4111 1111 1111 1111.'))
test_eq(r.answer, 'It is for [EMAIL], card [CARD].')
r.leaked
{'email': 1, 'card': 1}

pii='redact' masks the recognised identifiers in each section’s text, then lets a hosted model answer. A name is masked only when a title such as Dr comes before it, so “Ada Lovelace” goes through, as a real-model cell further down shows.

_seen.clear()
r = _v.ask('what is on invoice 4471?', pii='redact', mk_chat=_chat('remote', 'An invoice for 240.00 GBP [1]'))
test_eq('ada@example.com' in _seen['prompt'], False)
test_eq(_seen['runtime'], 'remote')
r.answer
'An invoice for 240.00 GBP [1]'

A structured answer (schema=) has its fields scrubbed the same way. An API key counts as personal information, so a hosted chat is refused for it just as for an email address, and so is a document that was marked by hand.

Against real models

These cells replay replies recorded from real models with CachedChat, so they run without the models. Each one shows one rule or one way a call can fail.

Nothing private: the default local model on its default backend answers and cites section [1].

r = model_ask(open_vault, q)
test_eq((r.model, r.runtime), (dflt_model, 'litert'))   # gemma-4-E2B on LiteRT, unasked for

test_eq(r.cited.attrgot('n'), [1])                      # it cited [1]...

r.answer
'Reciprocal rank fusion combines rankings from legs that share no vector space by summing $1/(60 + \\text{rank})$ over the legs [1].'

r = model_ask(open_vault, q, model=CLOUD)

Under pii='local', naming a hosted model= does not send private sections to it; the local pii_model answers instead. Naming the hosted model as pii_model does not work either: the check sees a hosted chat and refuses, and nothing is sent.

# naming a hosted model where the sections are private routes to the local one instead
test_eq(model_ask(private_vault, pq, model=CLOUD).runtime, 'litert')

r = model_ask(private_vault, pq, model=CLOUD, pii_model=CLOUD)   # ...and naming it as the *local* one is refused
test_eq((r.refused, r.runtime, r.answer.startswith('held back')), (True, 'remote', True))
# nothing was sent, and the proof is that there is nothing to replay: a call would have been
# recorded under one of these two keys, and neither is in the cache
_c = ch_fn(CLOUD).cache
for _sp in (VAULT_SP, PII_SP): assert f'{CLOUD}|call|{_sp}|{r.prompt}' not in _c
r.answer
'held back: these sections hold personal information (card, email, phone) and remote is not a local runtime, so nothing was sent to it'

pii='redact' masks the identifiers and a hosted model answers. “Ada Lovelace” has no title before it, so it is not masked and reaches the hosted model.
