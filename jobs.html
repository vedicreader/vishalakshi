jobs

A job queue kept in the vault file: work survives a crash, failures are retried with a growing delay, and jobs that keep failing are set aside for a person

Fetching a page, ingesting a batch of files or rebuilding the topic map can fail or be interrupted. Queue keeps such work as rows in a jobs table in the vault’s own SQLite file, so a job outlives the process that queued it, and no separate server is needed. enqueue adds a job. A worker takes jobs with claim, which marks them as running and gives the worker a lease: a time limit (lease, 10 minutes) on its claim. Two workers claiming at once never get the same job. If a worker dies, its lease runs out and reclaim puts the job back. A job that fails is retried after a delay that doubles each time, from 30 seconds up to 6 hours, and after max_attempts (5) failures it becomes dead: it stays in the table, with its error, for a person to look at.

Because the queue lives in the same file as the documents, a job queued inside a write_txn is committed together with the write that caused it. Queue needs only a database and knows nothing about a vault; acquire registers the vault’s own jobs on it.

The queue

A job has a kind, which names the handler that runs it, and a payload, a dict stored as JSON. key makes queueing idempotent: while a job with the same kind and key is still waiting or running, enqueueing it again returns that job instead of adding a second one, so re-running the same fan-out does not double the work. Lower priority runs first.

Claiming

claim picks and marks its jobs in a single SQL statement, and SQLite lets only one write run at a time, so another worker cannot slip in between the pick and the mark. What a worker gets back is already running and already leased.

ack (finished) and fail (failed) only count while the caller still holds the lease. A handler slower than lease has its job reclaimed and given to another worker. Without this check its late ack could mark as done a job another worker is still running, or its fail could send a finished job back for a third run. Instead the late call comes back lost, and the run history says so.

Running

A handler is a function fn(payload), registered with register or the on decorator. run_one runs one claimed job, and drain claims and runs until the queue is empty or limit jobs have run; it is what a cron job calls. How a handler ends decides what happens next:

the handler the job
returns normally is done
returns a dict with skipped is done, recorded as a skip, and not retried; the acquisition methods do this when a page has no transcript or is not a PDF
raises Retry is retried after Retry.after seconds or the backoff delay, using up an attempt; this is for work that did not fail but should run again, such as a page behind a bot wall
raises any other exception is retried after the backoff delay, and dead once its attempts are spent
raises Terminal is dead at once

Terminal is for failures that waiting cannot fix: a 401, a model name that does not exist, a file that is gone. With the default schedule a doomed job would otherwise be retried for most of a day. A job whose kind has no handler is dead at once for the same reason.

Looking at it

jobs lists jobs by state and kind, pending counts what is left, stats counts each state, and history lists past runs. Dead jobs are the queue’s inbox for a person: dead lists them with the error that finished them off, and since nothing is deleted on failure, retry simply puts one back with its attempt count reset. purge deletes finished jobs and run history older than keep (7 days) and leaves dead jobs alone.

Try it

from litesearch import database

db = database()
q  = Queue(db, lease=60, max_attempts=3, base=1)
seen = []
q.register('echo', lambda p: seen.append(p['n']) or dict(n=p['n']))
q.enqueue_all('echo', [dict(n=i) for i in range(3)])
q.drain('w1')
seen, q.stats()
([0, 1, 2], {'ready': 0, 'running': 0, 'done': 3, 'dead': 0, 'next_due': None})
